# Refresh, tracked history and Social V1

## Refresh and provider credits

The mobile refresh action reads `GET /v1/board` and `GET /v1/board/summary` from CrownIQ's server. Rankings are already part of the saved board; `GET /v1/rankings` is also read-only. No public GET route pulls odds or launches web research. The server saves the last validated board and evidence in `CROWNIQ_BOARD_CACHE_FILE` (default `tmp/board-cache.json`). At startup it reloads and **re-evaluates** that board against the current time and currently approved models, preserving the original `fetchedAt`. It never turns old odds into a newly fetched board. The app also has a local board cache and keeps filters and the Crown draft through refresh.

The app labels an available response LIVE if fetched within one minute, FRESH through five minutes, CACHED through 30 minutes and STALE thereafter. OFFLINE requires the platform to report disconnection; UNREACHABLE means the server request failed. These labels describe **the age of the provider board**, not a guarantee of live odds. The summary includes research and tracking readiness. A stale board remains visible with its age; GKR reevaluation drops rankings when event or evidence expires.

The signed-in owner can start a paid `POST /v1/owner/board/refresh` from Settings → Owner Board Analysis. It requires `acknowledgeProviderCost: true`, reports progress through `/v1/owner/board/status`, and preserves the prior board on failure. An optional admin token can also call paid `POST /v1/admin/refresh` or `POST /v1/admin/force-provider-refresh`; both require `x-confirm-provider-cost: yes` (428 without it) and share the owner job, so they return 409 while another pull runs. The Board tab's first-board recovery uses `POST /v1/owner/board/bootstrap`, which refuses with 409 once any board exists. There is **no automatic paid refresh schedule**; owner-controlled orchestration can later choose its own 10–15 minute cadence (or targeted near-event requests) within provider budgets. Ordinary app use will not schedule a 2-minute full-board pull. `POST /v1/admin/reanalyze` reuses odds already in memory and costs zero Odds API credits.

## Automatic decisions, grading and history

`ProductLedger` stores immutable selection snapshots in `CROWNIQ_PRODUCT_LEDGER_FILE` (default `tmp/product-ledger.json`). At publication of a board or completed web research it auto-tracks qualifying `CROWN_STRONG` and `CROWN_ELITE` decisions; `CROWNIQ_AUTO_TRACK_MIN_BAND=PLAYABLE` optionally admits PLAYABLE. PASS never qualifies. The SHA-256 decision identity includes event/player/market/threshold/direction/line type/model version, analysis and exact attributed evidence. Repeated reads and identical publications do not add records. A moved threshold or changed evidence/model snapshot creates a distinct record. The saved decision contains the original provider line, GKR breakdown, quality, board rank and research snapshot; grading updates only result fields. History is not used to change GKR weights or replace current confirmed role.

The same canonical decision can be graded once via owner `POST /v1/admin/tracked-results`, with sourced facts (`eventId`, `playerId`, `market`, `status`, `actual`, `sourceName`, `sourceUrl`, `completedAt`). An event/player/market result grades all distinct selected thresholds consistently. Missing results stay PENDING; DNP and VOID cannot contain a numeric result. Optional `CROWNIQ_NFLVERSE_AUTO_GRADE=true` plus `NFLVERSE_MAPPING_FILE` runs an hourly background worker using verified NFL game/player/team mappings and free nflverse weekly stats for passing yards, pass attempts, pass completions, rushing yards, rush attempts, receiving yards, receptions and targets. It waits for completed games and an actual matching row; missing data is retried. It neither calls Odds API nor guesses zero/DNP. Other sports require a mapped authoritative results feed or owner supplied sourced facts; they do not yet auto-grade.

`GET /v1/history/:sport/:playerId/:market` returns the ten most recent **unique graded events** for that player and market, labeled `CrownIQ Tracked L4` when there are only four. Numeric mean, median, variance and range use actual observed stats only; DNP/VOID have no numeric contribution. `fullArchiveCount` preserves every graded decision, including earlier lines and versions. The research contract labels this source `CROWNIQ_INTERNAL_HISTORY` and keeps `internalOutcomeDistribution` separate from GKR scores. History may inform future research only after explicit evidence mapping; it never automatically overrides current status, role or source authority. The full private ledger supports later calibration by sport, market, direction, line type, score band, model version, rank and danger-zone flag without changing production weights.

## Social V1

The five mobile tabs are Board, Rankings, Crowns, Social and My Picks; Settings is accessible from My Picks. The Social screen reads at most ten qualified profiles plus recent public Crowns from those ten. Its Following section reads at most 20 recent public Crowns from accounts the signed-in user follows; hidden, suspended, and unshared Crowns are excluded. Public profile and Crown detail views are paginated; no chat, notifications or large global feed. The app allows a user to **explicitly** request Share to Social; private drafts and internal automatic tracking never publish themselves. Public responses include public UUIDs, names, publicly shared leg snapshots and canonical grades; they omit private actor keys, internal tracked decision IDs, email, private picks, credentials, and wager amounts.

Writes require the server-authenticated CrownIQ account (or an explicitly injected trusted `socialActor` integration). Registration and login now provide that account identity; see [profile sign-in](PROFILE_SIGNIN.md). Clients cannot claim an actor by supplying a public ID. Sharing calls the engine's full Crown audit, including a trusted correlation policy. Without that policy, sharing fails closed with `CORRELATION_AUDIT_UNAVAILABLE`. An owner must provide the correlation policy before public Crowns can be published. No paid identity service was added.

Social routes: signed-in `GET /v1/social/top-users`, `/recent-crowns`, `/following-crowns`, `/user/:publicId`, `/user/:publicId/crowns?offset=&limit=`, `/crowns/:id`, `/crowns/:id/import-preview`; `POST /v1/social/profile`, `POST/DELETE /v1/social/follow/:publicId`, `POST /v1/social/crowns`, `DELETE /v1/social/crowns/:id`. `import-preview` compares the exact original event, player, market, direction, threshold and line type with the current server board. The mobile app repeats this read-only preview and board fetch **when the user taps Add**, adds only the exact available current line to a private draft, and displays changed alternatives without substituting one automatically. A draft is never represented as a server-approved Crown. Users can separately save a server-validated private Crown to their account via `/v1/me/crowns`.

### Leaderboard and privacy rules

- Qualification: at least **20 graded public selections** (WIN, LOSS or PUSH). DNP and VOID remain in record metadata but do not qualify as a played selection.
- Sorting: public wins descending; then public hit rate descending; then graded public selections descending; then stable public ID. Show only the Top 10. `hit_rate = wins / (wins + losses)`; with no wins or losses, hit rate is unavailable. PUSH, DNP and VOID are excluded from its denominator.
- The public leaderboard and recent Top 10 Crowns have a 180-second in-process cache; writes invalidate it. No WebSocket or polling loop is required.
- A user can unshare a Crown: remove it immediately from all public listings and detail routes, while preserving the private/internal history. Public grade credit from a legitimately shared selection is kept so unsharing after a loss cannot manipulate the leaderboard. Duplicate public credits for the same user and tracked decision are rejected.
- Profiles reserve `socialEnabled`, `profileVisible` and `isSuspended` fields for later account controls. Suspended/hidden profiles and their Crowns are excluded from public reads.

## Deployment and limits

The JSON ledgers use atomic rename and serialize mutations within one API process. Give `CROWNIQ_BOARD_CACHE_FILE` and `CROWNIQ_PRODUCT_LEDGER_FILE` durable storage; the defaults under `tmp/` are not durable on ephemeral hosts. This is **single-instance storage**; do not run multiple writers against the same file. Existing `DATABASE_URL` is reserved, not a configured production database or migration. A production multi-instance deployment needs a migration of these same snapshot and public ID rules to its shared database, plus trusted auth, correlation policy and authorized result feeds. None of this work changes the provider adapter or GKR scoring weights.
